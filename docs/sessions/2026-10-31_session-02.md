- **로그인에는 느슨한 URL 매칭을 쓰지 않는다.** 복사 단축키용 `match.js`(접두어+`*`)와 분리해

  IndexedDB는 디스크에 남아 "암호화 키 영구 저장 금지"에 위배되어 배제.
- **권한을 늘리지 않고 끝냈다.** 자동 잠금에 `alarms` 를 쓰지 않고 접근 시점 지연 평가로 처리.
- **계정 선택 UI는 페이지 안**에 띄우되(사용자가 보는 화면), 페이지 JS 노출을 줄이려고 라벨/마스킹된 아이디만 넣음.

  session: 10MB·인메모리·추가 권한 불필요·기본적으로 콘텐츠 스크립트 비노출.
  → 사이트당 1항목 분할 저장으로 결정(충돌 범위도 사이트 단위로 좁아짐).

# 추가 세션 — 2026-10-31 (session-02b) · 페이지 내 단축키 (F2)

## 목표
"단축키를 F2 로 등록할 수 없나?" → 가능 여부 확인 후, 가능한 방식으로 구현.

## 확인한 제약 (Chrome 공식 문서)
- 확장 단축키(`commands`)는 **`Ctrl` 또는 `Alt` 를 반드시 포함**해야 한다. 미디어 키만 예외.
- 지원 키 목록: `A–Z`, `0–9`, `Comma`, `Period`, `Home`, `End`, `PageUp`, `PageDown`, `Space`,
  `Insert`, `Delete`, 방향키, 미디어 키 → **`F1`~`F12` 없음**
- 매니페스트 제안 단축키는 최대 4개, 사용자가 `chrome://extensions/shortcuts` 에서 바꿀 때도 같은 규칙 적용
- 결론: **`F2` 단독은 commands API 로 등록 불가** (shortcuts UI 에서도 불가)

추가 확인:
- 매치 패턴의 **포트는 선택 사항**이며, 생략하면 모든 포트에 일치한다 → 포트 있는 origin도 다룰 수 있다.
- `registerContentScripts` 는 Chrome 96+, `scripting` 권한 필요, 같은 id 재등록 시 에러, `matches` 필수.

## 한 일
- `src/lib/hotkey.js` (신규) — 키 조합을 `"F2"`/`"Alt+Shift+L"` 같은 **정규화 문자열 1개**로 다루는 순수 로직
  (`comboFromEvent`, `normalizeHotkey`, `isFunctionCombo`, `needsTypingGuard`, `isTypingTarget`, `displayCombo`)
- `src/content/hotkey.js` (신규) — 캡처 단계 `keydown` 리스너. `storage.sync` 에서 조합을 직접 읽고
  `storage.onChanged` 로 갱신. 입력창 가드, 1.2초 연타 가드, `LOGIN_HOTKEY` 전송
- `src/lib/login-match.js` — `toMatchPattern` / `toMatchPatterns` 추가 (autoLogin ON 사이트만, 중복 제거, 포트 제거 옵션)
- `src/background/service-worker.js` — `syncHotkeyRegistration()` 추가.
  `onInstalled` / `onStartup` / `storage.onChanged(sync)` 에서 재등록, 패턴 0개면 등록하지 않음,
  포트 포함 패턴이 거부되면 포트 없는 패턴으로 재시도. `LOGIN_HOTKEY` 는 `sender.tab.id` 로 실행
- `src/lib/login-store.js` — `DEFAULT_SETTINGS.hotkey = { combo:"F2", enabled:true }`,
  `getSettings()` 가 중첩 객체를 얕게 덮지 않도록 수정
- UI — 설정 → 단축키 카드에 "자동 로그인 (등록 사이트 페이지)" 행 + **키 지정**(키 캡처) + 사용 On/Off + 주의사항 안내.
  자동 로그인 화면 힌트도 두 단축키를 함께 표시
- `tools/test-hotkey.mjs` (신규, 40종) + `test-all.mjs` 에 편입

## 결정 / 배운 점
- **전역 단축키를 없애지 않고 둘 다 유지**했다. 페이지 내 단축키는 주소창에 포커스가 있으면 못 받기 때문에
  서로를 대체하지 않고 보완한다.
- **등록 범위를 좁혔다.** `<all_urls>` 상시 주입이 아니라 `registerContentScripts` 로
  "자동 로그인이 켜진 사이트의 origin/경로"에만 심는다. 사이트를 지우면 리스너도 사라진다.
- 매치 패턴이 느슨해지는 부분(경로 접두어·포트)은 **`siteMatches()` 가 다시 엄격히 검사**하므로
  자격증명 주입 조건은 전역 단축키와 동일하다.
- **수정자 없는 글자키 가드**: F2 같은 기능키는 입력창에서도 받아야 하지만(아이디 칸에 커서가 있는 게 정상),
  `L` 같은 글자키를 지정하면 글자 입력을 막아버린다 → `needsTypingGuard()` 로 구분했다.
- 콘텐츠 스크립트는 ES 모듈이 아니라 lib 를 import 할 수 없다. 함수 3개를 복제하는 대신,
  **테스트가 파일에서 그 구간을 꺼내 lib 와 같은 입력으로 비교**하게 했다.
  일부러 한쪽만 틀리게 바꿔 테스트가 실패하는지 확인했다(실패 → 원복 후 통과).

## 1. 다중 계정 결함 수정 (지적이 맞았다)

`defaultAccountId` 가 설정돼 있으면 선택창을 **건너뛰고** 그 계정으로 바로 실행했다.
게다가 첫 계정을 추가하면 자동으로 기본 계정이 되므로 — **사실상 항상** 선택창이 안 떴고,
2번째 이후 계정은 등록만 되고 쓸 방법이 없었다. 즉 다중 계정 기능이 사실상 죽은 기능이었다.

- 기본 계정은 **선택창에서 맨 앞 정렬 + 포커스**만 담당하도록 변경
- 계정이 2개 이상이면 **항상 선택창**을 띄운다 (1개면 그대로 바로 실행)
- 선택창 키보드 조작 추가: `Enter`(포커스된 계정) · `숫자키` 바로 선택 · `↑↓` · `ESC`
  → 기본 계정을 쓸 때 추가 비용은 **키 하나(Enter)** 뿐
- 라벨 "기본" → "먼저" 로 변경해 의미를 맞췄다
- 회귀 테스트 추가: `accountCandidates` 가 기본 계정 지정 시에도 **나머지 계정을 모두 포함**하는지

## 2. 로그아웃 (같은 F2)

- 사이트별 **로그아웃 셀렉터**(`sel.logout`) + `autoLogout` 스위치 추가
- 판정: `AF_DETECT` 로 로그아웃 요소가 **DOM 에 있으면** 로그인 상태 → `AF_LOGOUT`(클릭), 없으면 자동 로그인
- **표시 여부는 보지 않는다** — 로그아웃 링크는 드롭다운 안에 숨어 있는 경우가 많고 숨은 `<a>` 도 JS 클릭으로 동작한다.
  대신 "로그인했을 때만 생기는 요소를 고르라"고 UI 에서 안내
- **로그아웃은 복호화가 필요 없으므로 잠금 체크보다 앞에 둔다** → 잠긴 상태에서도 로그아웃 가능
- 셀렉터가 비어 있으면 저장 시 `autoLogout` 을 자동으로 끈다
- 둘 다 못 찾은 경우를 구분해 안내 ("로그인 입력창도, 로그아웃 요소도 찾지 못했어요")

## 3. 패널 토글 (F4) — 제약이 가장 까다로웠다

확인한 사실 (공식 문서 + 조사):
- `chrome.sidePanel.close()` 는 **Chrome 141+** (open 은 116+)
- `open()` 은 **사용자 제스처**가 필요하다. 콘텐츠 스크립트의 키 입력은 유효한 제스처이고 메시지에 함께 전달되지만,
  **수신 측이 `await` 를 만나는 순간 사라진다**
- 패널이 열려 있는지 **묻는 API 가 없다**

→ 두 제약이 충돌한다: 열림 여부를 알려면 상태 조회가 필요한데, `storage` 조회(비동기)를 끼우면 제스처가 날아간다.

해결:
- 패널이 열려 있는 동안 `runtime.connect({name:"ua-sidepanel:<windowId>"})` **포트**를 유지
- 서비스 워커는 `openPanelWindows` **메모리 집합**으로 즉시(동기) 판단.
  포트가 연결돼 있으면 SW 가 살아 있으므로 집합을 신뢰할 수 있고, SW 가 죽었다면 집합이 비는데 그때는 패널도 닫힌 상태
- 패널 쪽은 포트가 끊기면(SW 재시작) 재연결
- 메시지 핸들러에서 `await` 없이 `open()`/`close()` 동기 호출
- `close()` 미지원 버전(141 미만)에서는 열기만 되고 안내 토스트

부수 변경: 단축키 리스너 등록 범위 기본값을 **모든 http(s) 페이지**로 올렸다.
F4(패널 토글)는 어디서든 쓰는 기능이라 "등록 사이트만"으로 두면 반쪽짜리가 된다.
설정의 **모든 사이트에서 사용** 을 끄면 기존처럼 등록 사이트에만 심는다(그럼 F2/F4 둘 다 좁아진다).

# 추가 세션 — 2026-10-31 (session-02d) · 로그아웃 매칭 버그 + 금고 안전장치

## 목표
1. 사용자 보고: "로그아웃할 때 등록되지 않은 사이트라고 뜨네"
2. 앞선 질문("동기화된 암호문은 같은 마스터키로만 열린다")에서 나온 **데이터 손실 위험** 3가지 방어 적용

## 1. 로그아웃 매칭 버그 (재현 → 수정)

재현:
```
등록: https://labdev.unipost.co.kr/redmine/login
      → describeSiteUrl 이 matchPath=true 로 제안하고, 사이트 추가 시 그대로 켜졌다
      → origin=https://labdev.unipost.co.kr, path=/redmine/login

일치   /redmine/login
불일치 /redmine/my/page   (경로 불일치)   ← 로그인하면 바로 여기로 간다
불일치 /redmine/issues/1  (경로 불일치)
```
즉 **로그인에 성공한 직후부터 매칭이 깨져** 로그아웃이 구조적으로 불가능했다.

수정:
- `findOriginMatchingSites()` 추가 — origin(프로토콜+도메인+**포트**)만 완전 일치, 경로는 보지 않음.
  **로그아웃 분기에만** 사용한다. 로그인은 기존 엄격 매칭 유지(경로로 로그인 페이지를 구분해야 하므로).
  로그아웃은 복호화를 하지 않으므로 origin 일치만으로도 자격증명 유출 위험이 없다.
- 사이트 추가 시 `matchPath` 를 **자동으로 켜지 않는다**(도메인 전체가 기본).
- origin 은 맞는데 경로 때문에 로그인이 막힌 경우 `PATH_MISMATCH` 로 **원인 + 해결책**을 안내
  (페이지 토스트 / 패널의 현재 탭 안내 / 체크박스 옆 경고). 조용히 실패하지 않게 하는 게 목적.

판정 흐름 검증 (DOM 상태까지 넣어 시뮬레이션):

| 상황 | 경로 일치 ON (기존 등록) | 경로 일치 OFF (신규 기본) |
|---|---|---|
| 로그인 페이지 | 로그인 실행 | 로그인 실행 |
| 로그인 후 /my/page | **로그아웃 실행** | **로그아웃 실행** |
| 로그인 후 /issues/1 | **로그아웃 실행** | **로그아웃 실행** |
| 세션 만료 /issues/1 | PATH_MISMATCH 안내 | 로그인 실행 |
| 다른 호스트 | NO_MATCH | NO_MATCH |

→ 기존 등록(경로 일치 ON)을 고치지 않아도 **로그인→로그아웃→로그인 한 바퀴가 동작**한다.

## 2. 금고 안전장치 3가지

### (a) 동기화 경합 차단 — 데이터 손실 방지
Chrome sync 는 키별로 도착하고 **순서를 보장하지 않는다.** 그래서:
```
PC A: 금고(salt_A) + 암호문 저장
PC B: ua_site_* 는 도착, ua_vault 는 미도착 → isInitialized()=false → "최초 설정" → salt_B 생성
      → 병합(키 단위 last-write-wins) → ua_vault=salt_B → PC A 암호문 영구 손실
```
`hasAnyLoginData()`(인덱스 또는 `ua_site_*` 존재)로 감지해 `initVault()` 가 `ERR_SYNC_PENDING` 으로 거부.
사이트 항목이 인덱스보다 먼저 온 경우까지 보려고 `storage.sync.get(null)` 로 접두어를 훑는다.

### (b) 키 지문 (`kf`) — 원인 진단
암호문마다 `SHA-256(raw key)` 앞 6바이트를 기록. 복호화 실패 시 "손상"과
**"다른 마스터 비밀번호로 암호화됨"(`KEY_MISMATCH`)** 을 구분해 안내한다.
- 보안 영향 없음: `ua_vault.verifier`(알려진 평문의 암호문)가 이미 동기화되고 있어 대조 수단은 그대로다.
  실제 방어선은 PBKDF2 60만회.
- 지문이 없는 예전 레코드는 **판단 보류(true)** → 기존 데이터와 호환.

### (c) 경고 문구
최초 설정 화면에 "다른 PC에서 이미 설정했다면 새로 만들지 말고 그 비밀번호를 입력하세요" 추가.

## 확인한 동작 (질문에 대한 답)
- 복호화 키는 **어디에도 영속 저장되지 않는다.** sync 에는 `salt`(비밀 아님) + `iterations` + `verifier` + 암호문만.
- `salt` 가 동기화되므로 같은 마스터 비밀번호 → **같은 키**가 유도된다. 그래서 키를 보내지 않고도 다른 PC 에서 열린다.
- 틀린 마스터 비밀번호는 `verifier` 검증에서 **잠금 해제 자체가 거부**된다. 반쯤 열려 쓰레기 값이 입력되는 상태는 없다.
  (설령 통과해도 AES-GCM 인증 때문에 복호화가 예외를 던진다 — 이중 방어)
